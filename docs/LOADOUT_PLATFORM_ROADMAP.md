# MH3G 本地配装器与在线配装平台路线图

## 结论

截至 2026-08-18，MH3G / MH3U 本地配装器和在线配装平台首期已经上线。修改器
`v1.3.0-beta.6` 已打通“选择配装 → 实时计算 → 本地 JSON → 发布到广场 → 筛选与详情 →
一键加入装备箱”的完整闭环。

MH3G 计划内功能至此阶段性完成，后续转入缺陷、数据和兼容性维护，不再扩展高风险存档字段。
最终能力清单、验证门禁、不做项以及跨作交接见
[MH3G 修改器阶段完成记录](MH3G_COMPLETION_RECORD.md)。下一条产品开发主线为 MH4G 接入。

已完成公开大厅、装备与发动技能 AND 筛选、合法配装筛选、只读详情弹窗、登录、昵称、发布
查重、点赞、举报、管理员后台和生产部署。邮箱注册、邮箱登录、绑定邮箱、忘记密码、获赞统计
和新版个人信息页已随 `v1.3.0-beta.2` 上线；`v1.3.0-beta.3` 增加本地自动配装搜索、独立倒计时和
结果多维排序，`v1.3.0-beta.4` 补齐 Windows 最大化按钮并进一步精简结果表，`v1.3.0-beta.5`
增加固定装备、手动超孔珠子、非自然护石技能组与重复装珠解剪枝；`v1.3.0-beta.6` 增加非模态自动配装窗口、
孔位圆点状态和装饰珠左右转移交互。Windows Release 已标记为 prerelease 并通过 SQLite、SSL 和 Qt 离屏交互门禁。

客户端默认使用 `https://mhed.desk.65h26i.top`。生产 AOKSend 当前尚未配置和启用，注册、验证码
及找回密码会提示邮件服务未配置；已有账号登录、昵称与获赞信息、广场浏览筛选、点赞举报、发布
和一键加入装备箱均正常可用。

本路线不会恢复已经停止的资料库、图片、实时模型、人物试衣间或游戏资源包。配装器只使用
确定性的参数表、文字界面和程序绘制的属性摘要；验证成功后再抽象跨游戏协议并接入在线服务。
在线服务的数据库、API、举报、账号和部署验收以
[`mhed-platform` 配装大厅实施计划](https://github.com/AlexQFMM2/mhed-platform/blob/main/docs/IMPLEMENTATION_PLAN.md)
为准；本文件保留修改器侧边界和跨游戏路线。

固定实施顺序为：

```text
MH3G 本地配装器
→ 配装交换协议与数据版本
→ 公开配装大厅、筛选和一键导入
→ 登录后举报和管理员处置
→ 后台创建用户及登录
→ 用户发布、删除和点赞
→ 邮箱注册、验证和找回密码
→ MH3G 功能阶段性完成并转入维护
→ 移植 MH4G
→ 移植 MHGU / MHXX
```

## 第一阶段：MH3G 本地配装器（已完成）

MH3G 页面、装备选择弹窗、装饰珠、技能矩阵、防御耐性汇总、本地 JSON、一键写入和本地自动配装搜索已完成；详细规格见
[MH3G 手动配装器页面实施计划](MH3G_LOADOUT_BUILDER_PLAN.md)。自动搜索固定具体武器，只返回自然合法组合。

### 数据层

状态：前置数据工程已完成。运行时静态数据已经统一迁移到只读
`data/mh3g.sqlite`，并包含武器、防具、技能、装饰珠及全游戏护石自然组合；
装备合法性引擎已经接入装备箱、单件编辑器和配装器，不再维护运行时静态 CSV。

`ID_res.arc` 继续作为道具、十二类武器和五个防具部位的存档 ID 权威来源。Dex 和游戏
参数只补充配装属性，不能把 Dex 主键、过滤后的数组行号或模糊名称直接写入存档。

需要生成并纳入 manifest 校验的数据包括：

- 武器类型、存档 ID、孔位以及配装所需的职业限制。
- 五部位防具的性别、剑士/枪手、稀有度、基础/最大防御、五耐性和孔位。
- 每件防具提供的技能树及点数。
- 装饰珠占孔、正负技能点及适用限制。
- 技能树、发动阈值、发动技能名称和相反技能。
- 护石品级、孔数、第一/第二技能及点数范围。

所有关联必须通过武器类型、部位和原始日文名建立显式 crosswalk；无法精确映射的记录可以
显示，但不得参与一键写入。人工 crosswalk 使用 JSON，生成器直接产出 SQLite；连续生成
两次必须得到相同数据库、manifest、逻辑哈希和文件哈希。

### 本地界面

左侧导航增加始终可用的“配装器”。没有读取存档时仍可设计、导出和导入配装；只有“一键
加入装备箱”需要当前存在已读取的角色文件。

首版采用手动配装，不实现自动搜索算法：

- 选择一把武器、头、胸、腕、腰、腿和一个护石。
- 使用配装器专用装备选择弹窗，不复用装备箱单件编辑器；按角色性别及剑士/枪手筛选，
  支持中文/英文名称，以及任意多个“技能系 + `>`/`≥`/`=`/`≤`/`<` + 有符号点数”的AND条件。
- 防具部位由用户点击的头、胸、腕、腰或腿格固定，弹窗不提供部位下拉框，也不能选择其他
  部位的防具。
- 分别配置每件装备和护石上的装饰珠。
- 实时汇总技能点、已发动技能、距离下一阈值的点数、防御和五耐性。
- 孔位超限、职业冲突、性别冲突和护石异常以红色显示具体原因。
- 风险提示不自动修正配装，也不禁止用户导出或写入；只有 ID、数组和文件边界等结构错误
  可以阻止操作。
- 支持本地导出、导入版本化的 `.mhloadout.json`，为后续在线协议提供真实使用样本。

### 一键加入装备箱

配装写入范围为武器、五件防具和护石，装饰珠写入它们各自的装备记录。程序先在内存中
解析全部目标记录并预留所需空格，全部可写且空间足够时才一次性提交：

- 使用 `ID_res.arc` 验证过的真实 `equipment_type + save_id`。
- 新建记录的所有其余字段使用各类型已经确认的默认值，不复制未知来源的原始字节。
- 不自动穿戴、不自动保存文件，只设置主窗口 dirty 并刷新装备箱。
- 任一记录失败时内存逐字节不变。
- 3DS 使用小端格式、Wii U 使用带36字节头的大端格式，逻辑配装内容保持一致。

### 第一阶段验收

- 十二种武器各抽查一套配装，五个防具部位、护石和三孔装饰珠全部覆盖。
- 技能点、发动阈值、防御、耐性和孔位计算与游戏/Dex 对照一致。
- 3DS 与 Wii U 私有样本分别验证一键创建，只改变预留的装备箱记录。
- 箱满、未映射 ID、批量中途失败时不改变任何内存和磁盘字节。
- 点击主窗口保存前磁盘文件不变；保存后重新读取能看到刚创建的全部装备。
- 未修改打开保存继续保持逐字节一致。
- Qt 5.15 本地构建、离屏冒烟测试和 Windows Action 通过。

## 第二阶段：统一配装交换协议（已完成）

本地配装器验收后冻结 `MH_LOADOUT` 版本1协议。协议只保存逻辑值，不包含完整存档、角色名、
文件头、平台偏移或原始装备记录：

```json
{
  "schema": "MH_LOADOUT",
  "schema_version": 1,
  "game": "mh3g",
  "data_version": "<manifest hash>",
  "name": "套装名",
  "gender": "male",
  "weapon": {},
  "armor": {},
  "charm": {}
}
```

装饰珠保存在武器、防具和护石各自的 `decorations` 字段中；技能合计、防御、耐性、风险和
点赞数不作为权威数据保存。导入后始终由当前游戏数据库重新计算。

服务器和客户端都按 `game + schema_version + data_version` 解析。后续数据表修正不得静默改变
旧配装含义；无法迁移的条目明确显示“数据版本不兼容”，禁止猜测其他装备。

## 第三阶段：公开配装大厅与一键导入（已完成）

修改器内优先增加不要求登录的“配装大厅”。服务器只接收标准化配装 JSON，永不上传存档
文件或角色信息。测试内容先通过版本化 seed 或服务器本地管理命令导入，不等待账号系统。

- 按游戏隔离数据；MH3G、MH4G、MHGU/XX 的装备 ID 不能混用。
- 支持装备多选、发动技能多选和关键词搜索；多选默认要求同时满足全部条件。
- 列表显示配装名、发布者、发动技能、基础/满强化防御、五耐性和操作；备注不占独立列。
- 支持最新发布和点赞最多排序以及稳定游标分页。
- 详情使用只读配装器弹窗并在本地重新计算，只保留“一键加入装备箱”操作。
- 合法性仍然只作提示；服务器仅拒绝破坏协议、越界或无法安全解析的数据。
- 断网、超时、错误 JSON 和不兼容数据版本不得改变当前本地配装或存档。

## 第四阶段：登录举报与管理员处置（已完成）

公开大厅提供登录后举报，原因包括文字不当、广告垃圾、恶意或无法导入的配装、侵权冒充
和其他原因。举报保存用户、内容与载荷哈希快照，同一用户限频且不能重复举报同一配装；举报数量
不会自动下架内容。

超级管理员通过独立 Admin 页面查看举报、隐藏、恢复、忽略和软删除配装，所有操作写入审计
日志；举报数量不会自动下架配装。

不接付费内容审核或大型违禁词库。套装名和备注保持纯文本并限制长度，其他文字问题依赖举报
和管理员人工处理。首版不提供图片、头像、附件、私信、关注、评论和推荐算法。

## 第五阶段：后台创建用户与登录（已完成）

第一版账号由管理员创建，不开放注册，邮箱可以为空：

- 普通用户默认无角色；登录身份与额外角色分开处理。
- 登录用户名仅用于认证；大厅只显示独立昵称和公开数字 ID。默认昵称为“用户 + 公开 ID”，用户可在修改器个人信息页修改。
- 密码使用 Argon2id 等成熟算法保存哈希，不保存明文。
- 超级管理员生成一次性临时密码，首次登录必须修改。
- 浏览器使用同站安全 Cookie，修改器使用数据库仅保存哈希的随机 Bearer Token；会话可撤销并
  具有闲置与绝对有效期。
- PostgreSQL 保存角色、权限、用户角色和角色权限关系；API 在服务端执行权限判断。
- 初始只保留 `super_admin` 管理角色，只有超级管理员能进入 Admin、管理用户和角色，以及处置
  配装和举报。
- 首个超级管理员通过服务器本地管理命令创建，最后一个可用超级管理员不能被禁用或撤销角色。
- 普通用户即使无角色，仍可按所有权管理自己的配装；全部管理操作写入审计日志。

## 第六阶段：发布与点赞（已完成）

登录用户可以发布和软删除自己的配装，并对同一配装最多点赞一次：

- 服务端重新解析配装并生成装备、技能和风险索引，不信任客户端摘要。
- 服务端按去除套装名并规范化装饰珠顺序后的内容指纹查重；相同配装不能通过改名或改备注重复上传。
- 点赞使用 `(user_id, loadout_id)` 数据库唯一约束和事务计数。
- 发布和点赞分别限流，异常点赞可在后台查看和清理。
- 文字限制、举报、隐藏和审计机制继续生效。

## 第七阶段：邮箱注册与验证（已完成）

核心大厅和发布闭环稳定后，再开放用户名、密码和唯一邮箱注册：

- 邮箱验证、邮箱登录、绑定/更换邮箱、忘记密码和重置密码；邮件 Provider 使用 AOKSend API v2。
- 邮件使用 PostgreSQL Outbox 重试，不提前引入 Redis 或消息队列。
- 首版不启用人机验证，使用注册、登录、重发邮件和点赞接口限流；出现实际滥用后再增加。
- Desk 个人信息页使用蓝白账号中心，登录后显示昵称、公开 ID、验证邮箱和当前公开配装获赞数。

AOKSend 文档：<https://www.aoksend.com/api.html>、<https://www.aoksend.com/check_balance_api.html>。

## MH4G 接入（本地已完成，未部署）

MH4G 复用 MH3G 已验证的七格交互、长列表规则、逻辑协议外壳、账号和广场流程，但游戏数据、
计算器、合法性和存档写入器保持完全独立。工作区现有 `mh4g-se` 已具备加密存档核心、十四类
武器、1400格道具箱、1500格装备箱、28字节装备记录、发掘装备和猎虫编辑能力。

截至 2026-08-18，上述接入已在本地工作区完成：独立 `mh4g.sqlite`、七格配装器、技能与
面板计算、社区合法性、发掘筛选、平台游戏子表和 Admin 审核均已实现。MH4G 没有复刻页面，
而是直接沿用本项目已经验证的配装器、大厅、个人信息、关于页和长列表交互。

MH4G 协议不是 ID-only 简化载荷。武器、五件防具和护石各保存完整 28 字节实例，因而可以
无损表达发掘攻击、防御、耐性、斩味、固定装饰珠、极限强化、护石 16 位点数、猎虫和未知
保留字节。详情仍以只读配装器弹窗打开，一键加入预检全部 1,500 格后事务式写入七条记录。

合法性没有套用不完整的护石/发掘推断规则，而是使用可举报、可由管理员修正的合法、非法、
不确定三态。是否包含发掘装备由服务端按原生 ID 派生，不能由客户端声明；护石不计入，普通
ID 携带随机参数也不改变分类。结构长度、未知 ID、部位和记录 ID 不一致仍严格拒绝。

这批 MH4G 变更已推送到 `mh4g-se/main` 并通过 Windows Action 生成测试 Artifact，但尚未创建
发布标签或部署；生产平台和 MH3G `v1.3.0-beta.5` 不受影响。
后续上线必须先导入两份游戏 SQLite、备份 PostgreSQL、执行追加迁移 00005 并完成双游戏
readiness 验收。任何跨作展示继续依赖 `game + schema_version + data_version`，不建立装备
ID 偏移、名称猜测或整份存档转换。

MHGU / MHXX 排在 MH4G 闭环之后。GU 与 XX 即使共享部分游戏数据，也继续使用各自已验证的
文件布局，不转换整份存档。

## 成本边界

配装仅为文本和小型 JSON，首版使用现有服务器、关系数据库和普通索引，不引入图片、对象
存储、Elasticsearch 或 CDN。HTTPS 使用免费证书；可预见的新增成本主要是验证邮件和数据库
备份。规模增长前不提前建设复杂基础设施。
