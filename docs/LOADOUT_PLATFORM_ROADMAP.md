# MH3G 本地配装器与在线配装平台路线图

## 结论

MH3G / MH3U 本地手动配装器已完成，当前进入本地与实机验收阶段。它已打通
“选择配装 → 实时计算 → 本地 JSON → 一键创建到装备箱”的核心闭环。

本路线不会恢复已经停止的资料库、图片、实时模型、人物试衣间或游戏资源包。配装器只使用
确定性的参数表、文字界面和程序绘制的属性摘要；验证成功后再抽象跨游戏协议并接入在线服务。

固定实施顺序为：

```text
MH3G 本地配装器
→ 配装交换协议与数据版本
→ 用户注册、登录和邮箱验证
→ 管理后台
→ 在线配装广场
→ 广场配装一键加入存档
→ 移植 MH4G
→ 移植 MHGU / MHXX
```

## 第一阶段：MH3G 本地配装器

MH3G 首版页面、装备选择弹窗、装饰珠、技能矩阵、防御耐性汇总、本地 JSON 和一键写入已完成；详细规格见
[MH3G 手动配装器页面实施计划](MH3G_LOADOUT_BUILDER_PLAN.md)。首版明确不实现自动推荐，
配装发现由后续在线广场承担。

### 数据层

状态：前置数据工程已完成。运行时静态数据已经统一迁移到只读
`data/mh3g.sqlite`，并包含武器、防具、技能、装饰珠及全游戏护石自然组合；
装备合法性引擎已经接入装备箱、单件编辑器和配装器，不再维护运行时静态 CSV。

`ID_res.arc` 继续作为道具、十二类武器和五个防具部位的存档 ID 权威来源。Dex 和游戏
参数只补充配装属性，不能把 Dex 主键、过滤后的数组行号或模糊名称直接写入存档。

需要生成并纳入 manifest 校验的数据包括：

- 武器类型、存档 ID、孔位以及配装所需的职业限制。
- 五部位防具的性别、剑士/枪手、稀有度、基础/最大防御、五耐性和孔位。
- 每件防具提供的技能树及点数。
- 装饰珠占孔、正负技能点及适用限制。
- 技能树、发动阈值、发动技能名称和相反技能。
- 护石品级、孔数、第一/第二技能及点数范围。

所有关联必须通过武器类型、部位和原始日文名建立显式 crosswalk；无法精确映射的记录可以
显示，但不得参与一键写入。人工 crosswalk 使用 JSON，生成器直接产出 SQLite；连续生成
两次必须得到相同数据库、manifest、逻辑哈希和文件哈希。

### 本地界面

左侧导航增加始终可用的“配装器”。没有读取存档时仍可设计、导出和导入配装；只有“一键
加入装备箱”需要当前存在已读取的角色文件。

首版采用手动配装，不实现自动搜索算法：

- 选择一把武器、头、胸、腕、腰、腿和一个护石。
- 使用配装器专用装备选择弹窗，不复用装备箱单件编辑器；按角色性别及剑士/枪手筛选，
  支持中文/英文名称，以及任意多个“技能系 + `>`/`≥`/`=`/`≤`/`<` + 有符号点数”的AND条件。
- 防具部位由用户点击的头、胸、腕、腰或腿格固定，弹窗不提供部位下拉框，也不能选择其他
  部位的防具。
- 分别配置每件装备和护石上的装饰珠。
- 实时汇总技能点、已发动技能、距离下一阈值的点数、防御和五耐性。
- 孔位超限、职业冲突、性别冲突和护石异常以红色显示具体原因。
- 风险提示不自动修正配装，也不禁止用户导出或写入；只有 ID、数组和文件边界等结构错误
  可以阻止操作。
- 支持本地导出、导入版本化的 `.mhloadout.json`，为后续在线协议提供真实使用样本。

### 一键加入装备箱

配装写入范围为武器、五件防具和护石，装饰珠写入它们各自的装备记录。程序先在内存中
解析全部目标记录并预留所需空格，全部可写且空间足够时才一次性提交：

- 使用 `ID_res.arc` 验证过的真实 `equipment_type + save_id`。
- 新建记录的所有其余字段使用各类型已经确认的默认值，不复制未知来源的原始字节。
- 不自动穿戴、不自动保存文件，只设置主窗口 dirty 并刷新装备箱。
- 任一记录失败时内存逐字节不变。
- 3DS 使用小端格式、Wii U 使用带36字节头的大端格式，逻辑配装内容保持一致。

### 第一阶段验收

- 十二种武器各抽查一套配装，五个防具部位、护石和三孔装饰珠全部覆盖。
- 技能点、发动阈值、防御、耐性和孔位计算与游戏/Dex 对照一致。
- 3DS 与 Wii U 私有样本分别验证一键创建，只改变预留的装备箱记录。
- 箱满、未映射 ID、批量中途失败时不改变任何内存和磁盘字节。
- 点击主窗口保存前磁盘文件不变；保存后重新读取能看到刚创建的全部装备。
- 未修改打开保存继续保持逐字节一致。
- Qt 5.15 本地构建、离屏冒烟测试和 Windows Action 通过。

## 第二阶段：统一配装交换协议

本地配装器验收后冻结 `MH_LOADOUT` 版本1协议。协议只保存逻辑值，不包含完整存档、角色名、
文件头、平台偏移或原始装备记录：

```json
{
  "schema": "MH_LOADOUT",
  "schema_version": 1,
  "game": "mh3g",
  "data_version": "<manifest hash>",
  "name": "套装名",
  "weapon": {},
  "armor": {},
  "charm": {},
  "decorations": {},
  "summary": {}
}
```

服务器和客户端都按 `game + schema_version + data_version` 解析。后续数据表修正不得静默改变
旧配装含义；无法迁移的条目明确显示“数据版本不兼容”，禁止猜测其他装备。

## 第三阶段：账号与认证

在线服务使用现有服务器和域名。公开浏览不要求登录，发布、编辑、删除和点赞要求已验证账号。

- 用户名、密码和唯一邮箱注册。
- 密码使用 Argon2id 等成熟算法保存哈希，不保存明文。
- 邮箱验证、忘记密码和重置密码；AOKSend 作为候选邮件 API。
- 开发期使用免费额度，正式期优先评估15元/万封的极速版，并用一个通用安全验证码模板覆盖
  注册验证和密码重置。
- 短期访问令牌、可撤销的长期会话和设备列表。
- 首版不启用人机验证，使用注册、登录、重发邮件和点赞接口限流；出现实际滥用后再增加。

## 第四阶段：管理后台

管理后台与普通用户权限分离，至少包含：

- 用户搜索、查看、禁用、解封和软删除。
- 配装搜索、隐藏、恢复和软删除。
- 异常点赞查看和清理。
- 注册、验证、发布、点赞及接口错误统计。
- 管理员操作审计日志。

首版不提供用户头像、图片上传、私信、关注、邮件通知和推荐算法，避免对象存储、内容审核和
邮件成本扩张。

## 第五阶段：在线配装广场

修改器内增加“配装广场”，服务器只接收标准化配装 JSON，永不上传存档文件或角色信息。

- 发布时填写发布者账号、套装名和套装备注。
- 按游戏隔离数据；MH3G、MH4G、MHGU/XX 的装备 ID 不能混用。
- 支持装备多选、发动技能多选和关键词搜索；多选默认要求同时满足全部条件。
- 列表显示发布者、套装名、备注、主要技能、发布时间和点赞数。
- 支持最新发布和点赞最多排序；登录用户对同一配装最多点赞一次。
- 详情页先导入本地配装器并重新计算，显示数据版本和全部风险，再允许一键加入装备箱。
- 合法性仍然只作提示；服务器仅拒绝破坏协议、越界或无法安全解析的数据。

## 后续移植

MH3G 闭环稳定后复用 UI、协议、账号和广场接口，但各作的数据生成器与存档写入器保持独立：

- MH4G 增加十四武器、发掘装备和4G专属护石/装备规则；首版可先排除发掘装备。
- MHGU 与 MHXX 共用游戏数据 ID 和逻辑配装，分别沿用已有文件布局；GU/XX 之间仍不转换
  整份存档。
- 任何跨作展示都依赖服务器的 `game` 字段，不建立装备 ID 偏移或模糊名称映射。

## 成本边界

配装仅为文本和小型 JSON，首版使用现有服务器、关系数据库和普通索引，不引入图片、对象
存储、Elasticsearch 或 CDN。HTTPS 使用免费证书；可预见的新增成本主要是验证邮件和数据库
备份。规模增长前不提前建设复杂基础设施。
