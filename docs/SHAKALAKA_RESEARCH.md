# MH3G 奇面族修改研究记录

本文记录从 MH3G 汉化版 CCI 解包资源中确认的奇面族（茶茶、卡扬巴）原生编号，作为后续
存档字段定位、编辑界面和合法性提示的依据。当前仅完成资源调查，尚未在修改器中加入奇面族
编辑功能。

## 证据来源

- 解包目录：`D:\MH\mh3G\cci_unpacked`
- 面具参数：`romfs\arc\ainpc\ainpc.arc` 内的 `ainpc/ainpcdata`
- 菜单文字：`romfs\arc\ID\ID_lb.arc` 内的 `GUI/font/lobby/Facility_jpn`
- 舞蹈声音资源：`snd_ainpc_dance00.arc`～`snd_ainpc_dance04.arc`，以及对应的
  `snd_ainpc02_dance00.arc`～`snd_ainpc02_dance04.arc`
- 交叉核对：MH3G Wiki 的面具、[舞蹈](http://wiki.gotvg.com/mh3g/index.php?title=舞蹈)和
  [特技](http://wiki.gotvg.com/mh3g/index.php?title=特技)页面

汉化版使用替换字体，直接按 Unicode 解码会出现错字。因此，资源数组的顺序和数量可作为
原生 ID 证据；中文名称需结合 Wiki、实际游戏画面或汉化字库映射校准。

## 公共解锁与个人状态模型

当前按以下两层结构研究和设计编辑器：

- 账号级公共池：已获得面具、已习得舞蹈、已习得特技；茶茶和卡扬巴都可从同一份列表选择。
- 奇面族个人状态：当前装备面具、当前舞蹈与特技方案，以及各面具熟练度等成长数据。

这一模型同时得到游戏机制与存档结构支持：

- Wiki 的五种舞蹈只有一份习得表，其中同时出现“茶茶加入时习得”和“卡扬巴加入时习得”，
  没有给两人分别维护舞蹈所有权。
- Wiki 的特技也只有一份统一“入手方法”表，没有分别列出茶茶特技与卡扬巴特技。
- 火龙面具的已获得位位于两份个人记录之外，而当前装备面具位于茶茶个人记录内。
- 面具熟练度明确不共享：Wiki 说明茶茶把某面具练至 Lv5 后改给卡扬巴装备，卡扬巴在该面具上
  的熟练度仍然很低。因此“共享面具所有权”不能被误写成“共享面具熟练度”。

公共池的整体设计已可确定，但目前只确认了火龙面具的具体获得位；舞蹈与特技公共位图的准确
偏移和每一位映射仍须用单变量样本确认。

## 产品边界

奇面族数据现阶段只保留为只读研究，不加入修改器写入功能：

- 面具、舞蹈和特技的公共解锁与任务、剧情、交易和成长进度关联。直接修改解锁位可能造成
  事件状态不一致，严重时可能影响后续流程，因此不提供“全部解锁”或逐项解锁修改。
- 茶茶与卡扬巴的当前方案本身可在游戏菜单中调整。编辑器若允许选用尚未解锁的面具、舞蹈或
  特技，会制造游戏正常流程中不存在的状态，因此没有足够的功能收益来承担写入风险。
- 面具熟练度属于个人成长数据，理论上较适合修改，但仍需先确认每名奇面族、每个面具对应的
  完整字段、自然上下限和关联状态；在这些关系得到单变量样本验证前同样不开放写入。

后续调查的价值主要是补全 MH3G 存档结构和只读诊断能力，而不是以解锁修改为目标。除非未来
获得充分样本并重新评估产品边界，否则修改器不展示奇面族编辑入口。

## 当前结论与后续验证

- 面具逻辑 ID `0～22` 已确认。
- 舞蹈逻辑 ID `0～4` 已确认，中文显示名还需校准部分字形。
- 正常可装备特技 ID `0～30` 已确认。
- 3DS 茶茶记录基址已由单变量样本确认在 `0x7084`；当前面具位于记录偏移 `+0x00`，
  周围结构表明字段为小端 `uint16_t`。卡扬巴记录和 Wii U 对应位置仍待确认。
- 3DS 存档没有直接保存 XFS 面具逻辑 ID：古代面具和大炮面具的存档值分别为 15、17。
  后续仍需用单变量样本补全面具存档 ID 映射，并定位舞蹈、特技和公共习得状态。
- 面具的“已获得”状态位于两名奇面族固定记录之外的全局位图区；火龙面具已确认对应
  `0x62C5` 的 `0x40` 位。结合游戏中两人均从已获得面具中选择装备，当前按共享面具仓库建模。
- 在存档映射完成前，不实现写入功能；未知字段继续原样保留。
- 如果未来允许非自然组合，继续遵循项目现有原则：明确提示风险，但不主动限制用户保存。

## 3DS 单变量存档差分

私有样本只用于本地研究，不提交 Git：

| 样本 | SHA-256 | 操作 |
| --- | --- | --- |
| `user3` | `3611bb0b23dc2aa936c6dd1d8145d4c8fe7d2f6e42f763a037fbca5feb976c99` | 通关基线，茶茶装备古代面具 |
| `user3-chacha-mask-change` | `2b5f12dfcd0f8b38b1146ddee812ba78d7ca3abc4e703fb14f19a0e3bcaf95c4` | 只把茶茶更换为大炮面具后保存 |
| `user3-unlock-fire` | `7e3952dcf800ed8b6711fed96232565fc16b0a32c865d03fd36f8f14ec54627a` | 以上一份样本为基线，制作并解锁火龙面具 |

两份 35,328 字节的 3DS 存档只有六个字节不同：

- `0x0028`：保存产生的计时数据变化。
- `0x56E4～0x56E7`：保存校验值变化。
- `0x7084`：`0x0F → 0x11`，唯一的奇面族状态变化。

由此确认 3DS 存档 `0x7084` 是茶茶当前面具字段的低字节；字段按周围结构看是小端
`uint16_t`，本次值为 `0x000F → 0x0011`。`0x7084` 前方还存在一份结构相同、相距
`0x148` 字节的固定记录（候选基址 `0x6F3C`），高度可能是卡扬巴记录。需要通过只更换
卡扬巴面具的样本最终确认角色顺序和 `0x148` 记录步长。

本次差分也证明存档面具值不能直接套用 XFS 的 `Mask0～Mask22` 下标：古代面具的 XFS
逻辑 ID 为 2，而存档当前值为 15；大炮面具的存档值为 17。存档值可能采用模型资源编号，
后续必须建立独立的“显示面具 / XFS 参数 ID / 模型资源 ID / 存档 ID”交叉表。

### 火龙面具解锁位

`user3-unlock-fire` 以 `user3-chacha-mask-change` 为直接基线。除保存计时和校验值外，业务
差分与 Wiki 所列火龙面具制作费用逐项吻合：

| 存档偏移 | 变化 | 含义 |
| ---: | --- | --- |
| `0x0482` | `33 → 30` | 一组制作素材减少 3 个 |
| `0x0916` | `17 → 14` | 一组制作素材减少 3 个 |
| `0x093A` | `2 → 1` | 一组制作素材减少 1 个 |
| `0x5CCC` | `20515 → 19315` | 资源点减少 1200 |
| `0x62C5` | `0x31 → 0x71` | 只新增 `0x40` 位，火龙面具变为已获得 |

Wiki 的原生制作条件为资源 1200pt、狱炎石×3、火龙逆鳞×1、火龙上鳞×3。素材数量和资源点
全部对应后，剩余的 `0x62C5` 单比特变化可确认是火龙面具的已获得标志。该偏移不在茶茶
`0x7084` 或候选卡扬巴 `0x6F3C` 的固定记录内，因此面具获得状态属于全局共享仓库；两人的
当前装备面具仍分别保存在各自记录中。

此前在 `0x7490` 附近发现的全开位图在本次解锁中没有变化，所以它不是火龙面具获得标志；
它是否对应舞蹈或特技习得状态仍需单变量样本验证。
